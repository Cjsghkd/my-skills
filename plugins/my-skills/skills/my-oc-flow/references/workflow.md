# 기능 메모에서 검증까지


1. **조사** — survey 역할이 기존 진입점, 호출부, 실행 방법, 현재 동작과 미확인을 찾는다. UI 작업은 해당 화면과 사용자 동작에 맞는 프로젝트 경로만 조회한다. 경로가 없어도 조사 단계에 문서나 화면 목록을 만들지 않는다. 메모가 명확하면 메인이 기준을 그대로 기록한다. 해석이 필요한 경우에만 criteria 역할이 관찰 가능한 기대 결과를 제안한다. 제품 선택으로 범위가 바뀌면 사용자에게 묻는다.
2. **설계 작성** — design 역할로 새 세션 둘을 열어 가능하면 병렬 실행한다. 각각 기존 동작, 변경 범위, 실패 경로, 기준별 테스트와 UI 시나리오를 제시한다. D1이 두 안의 근거와 이견을 유지한 채 plan을 작성한다.
3. **설계 리뷰** — plan_review 역할로 별도의 새 세션 둘을 열어 같은 plan을 검토한다. 구현을 잘못해도 통과할 테스트가 있는지 확인한다. 아래 판정 규칙을 따르고 수정된 plan은 다시 평가한다.
4. **구현** — implement 역할의 **새 세션**에 확정안과 검증 방법을 준다. 연결된 호출부와 기존 오류 처리를 확인하고 필요한 범위만 변경한다. 특정 회귀를 잡는 테스트를 남긴다. 구현 종료 시 node <skill>/scripts/changes.mjs <id> <수정한 파일들>로 실제 diff를 저장하고 implementation 입력의 diff에 출력 경로를 연결한다. 기존 미커밋 변경이 섞인 파일은 기준이 HEAD임을 알린다. 설계의 전제가 무너지면 해당 항목을 설계에 돌려보낸다.
5. **실행 검증** — verify 역할이 현재 버전에서 실제 명령을 실행하고 명령·기대·관측·근거를 기록한다. 실패를 실행 환경 문제와 제품 결함으로 구분한다. 코드가 바뀌면 새 구현 기록과 검증을 남긴다.
6. **독립 코드 리뷰와 UI 확인** — code_review 역할의 새 세션 둘이 같은 변경본을 본다. UI 영향이 있으면 [UI 경로 조회·재생·저장](device.md)에 따라 같은 빌드에서 기기 확인을 병렬 실행한다. 저장된 경로의 마지막 검사가 이번 기준과 맞으면 그대로 재생한다. 새 동작은 시작 상태를 복원해 다시 통과한 뒤 해당 경로만 프로젝트에 저장한다. 호스트의 동시 세션 한도를 지키고 슬롯이 모자라면 대기 작업을 순차 실행한다. 병렬 검사 중 대상 코드는 고정한다.
7. **수정** — 리뷰와 기기 확인에서 채택된 같은 원인을 묶어 새 implement 세션이 수정한다. 최신 변경본에 대해 검증하고 기존 리뷰어가 변경 영향을 다시 본다. 유효한 이전 근거는 영향이 없는 이유와 실행한 버전을 기록해 재사용한다. 중요한 범위가 미확인이면 불완료 보고서를 제공한다.
8. **종료** — 각 단계 기록 후 같은 로컬 HTML이 갱신된다. finish 전에 status로 확인한다. 완료 기준·증거·남은 문제·절대 경로 보고서 링크를 채팅에 남긴다. 사용자가 Notion 기록을 요청하면 [선택 연동](notion.md)을 따른다. 기능 작업 호출 자체로 커밋·푸시·외부 게시를 수행하지 않는다.

## 독립 판정

기기 재생의 텍스트·상태 단언으로 판단할 수 없는 시각 기준이 있으면 visual 역할에 해당 캡처, 기대 상태, 기준 ID를 전달한다. 메인이 관찰 결과를 해당 device 기록에 포함한다.

두 리뷰어는 각각 독립 결과를 제출한다. 구체적인 주장에 동일한 issue ID를 붙인다. 메인은 동일 원인만 한 ID로 대응시키고 불명확하면 작성자에게 확인한다. 한쪽만 발견한 지적은 상대에게 근거와 쟁점을 주고 추가 의견을 받는다. 양쪽이 인정하면 수정하고 모두 기각하면 근거를 남긴다. 명시적 채택 대 기각만 `arbiter` 역할의 새 세션에 보낸다. 재현 또는 코드 근거가 부족하면 미확인으로 둔다. 제품 정책 선택은 사용자가 담당한다. 사용량이 없으면 미측정으로 기록한다.
