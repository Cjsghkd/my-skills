# My OC Flow

사용자와 대화하는 메인은 진행, 자료 전달, 사용자 선택, 결과 기록을 담당한다. 설계 판단과 코드 작성은 아래 역할에 맡긴다. 응답은 사용자 언어로 작성한다.

## 시작과 재개

이 파일을 기준으로 scripts/flow.mjs와 scripts/setup.mjs의 절대 경로를 구한다. 명령의 작업 디렉터리는 항상 **사용자가 개발할 Git 저장소 루트**다. 마켓플레이스 저장소에서 대상 코드를 수정하지 않는다.

- 새 실행은 메모를 그대로 UTF-8 파일에 보관한 뒤 `node <skill>/scripts/flow.mjs init <id> <memo-file>`. 짧은 영문 작업 ID를 고른다. 기존 실행은 `status <id>`로 최신 단계와 변경본을 읽고 미완료 지점부터 진행한다.
- 실행 기록은 [기록 규약](references/records.md)을 따른다. 작업별 JSON 입력·로그·이미지는 .flow/<id>/ 아래에 둔다. 부모만 record 명령을 직렬 실행한다. 하위 세션은 각자 담당한 결과를 반환한다.
- 메인은 gpt-6.1-terra / low 권장이다. 본문은 현재 메인 대화의 모델을 전환하지 않는다. 역할 모델은 roles.json의 설정을 사용한다.
- **Codex 하위 에이전트를 직접 호출한다.** 프로젝트 역할(my_oc_*)이 등록되어 있으면 사용한다. 또는 호스트가 모델·effort를 개별 지정할 수 있으면 roles.json의 모델·effort·지시를 적용해 새 작업 문맥을 연다. 역할이 준비되지 않은 환경에서는 설치 방법과 남은 단계를 알린다. 대체 모델이나 메인의 자기 리뷰로 결과를 채우지 않는다. 프로젝트에 역할 설치가 필요하면 setup.mjs PROJECT로 충돌을 확인하고 프로젝트 설정 변경을 사용자가 선택한 뒤 --install을 사용한다. 새 Codex 대화에서 역할 발견을 확인한다.
- 하위 세션에는 최초 메모, 확정 기준, 담당 역할, 현재 변경본, 필요한 파일 위치만 전달한다. 두 독립 세션에는 같은 원본 근거를 제공하고 첫 판단 전에는 다른 쪽 의견을 전달하지 않는다. 전체 채팅이나 스크린샷 모음을 공유하지 않는다.

## 진행

1. **조사** — survey 역할이 기존 진입점, 호출부, 실행 방법, 현재 동작과 미확인을 찾는다. 메모가 명확하면 메인이 기준을 그대로 기록한다. 해석이 필요한 경우에만 criteria 역할이 관찰 가능한 기대 결과를 제안한다. 제품 선택으로 범위가 바뀌면 사용자에게 묻는다.
2. **설계 작성** — design 역할로 새 세션 둘을 열어 가능하면 병렬 실행한다. 각각 기존 동작, 변경 범위, 실패 경로, 기준별 테스트와 UI 시나리오를 제시한다. D1이 두 안의 근거와 이견을 유지한 채 plan을 작성한다.
3. **설계 리뷰** — plan_review 역할로 별도의 새 세션 둘을 열어 같은 plan을 검토한다. 구현을 잘못해도 통과할 테스트가 있는지 확인한다. 아래 판정 규칙을 따르고 수정된 plan은 다시 평가한다.
4. **구현** — implement 역할의 **새 세션**에 확정안과 검증 방법을 준다. 연결된 호출부와 기존 오류 처리를 확인하고 필요한 범위만 변경한다. 특정 회귀를 잡는 테스트를 남긴다. 구현 종료 시 node <skill>/scripts/changes.mjs <id> <수정한 파일들>로 실제 diff를 저장하고 implementation 입력의 diff에 출력 경로를 연결한다. 기존 미커밋 변경이 섞인 파일은 기준이 HEAD임을 알린다. 설계의 전제가 무너지면 해당 항목을 설계에 돌려보낸다.
5. **실행 검증** — verify 역할이 현재 버전에서 실제 명령을 실행하고 명령·기대·관측·근거를 기록한다. 실패를 실행 환경 문제와 제품 결함으로 구분한다. 코드가 바뀌면 새 구현 기록과 검증을 남긴다.
6. **독립 코드 리뷰와 UI 확인** — code_review 역할의 새 세션 둘이 같은 변경본을 본다. UI 영향이 있으면 [Android 기기 확인](references/device.md)을 같은 빌드에서 병렬 실행한다. 호스트의 동시 세션 한도를 지키고 슬롯이 모자라면 대기 작업을 순차 실행한다. 병렬 검사 중 대상 코드는 고정한다.
7. **수정** — 리뷰와 기기 확인에서 채택된 같은 원인을 묶어 새 implement 세션이 수정한다. 최신 변경본에 대해 검증하고 기존 리뷰어가 변경 영향을 다시 본다. 유효한 이전 근거는 영향이 없는 이유와 실행한 버전을 기록해 재사용한다. 중요한 범위가 미확인이면 불완료 보고서를 제공한다.
8. **종료** — 각 단계 기록 후 같은 로컬 HTML이 갱신된다. finish 전에 status로 확인한다. 완료 기준·증거·남은 문제·절대 경로 보고서 링크를 채팅에 남긴다. 사용자가 Notion 기록을 요청하면 [선택 연동](references/notion.md)을 따른다. 기능 작업 호출 자체로 커밋·푸시·외부 게시를 수행하지 않는다.

## 독립 판정

두 리뷰어는 각각 독립 결과를 제출한다. 구체적인 주장에 동일한 issue ID를 붙인다. 메인은 동일 원인만 한 ID로 대응시키고 불명확하면 작성자에게 확인한다. 한쪽만 발견한 지적은 상대에게 근거와 쟁점을 주고 추가 의견을 받는다. 양쪽이 인정하면 수정하고 모두 기각하면 근거를 남긴다. 명시적 채택 대 기각만 arbiter 새 세션(gpt-6.2-sol / high)에 보낸다. 재현 또는 코드 근거가 부족하면 미확인으로 둔다. 제품 정책 선택은 사용자가 담당한다. 사용량이 없으면 미측정으로 기록한다.
